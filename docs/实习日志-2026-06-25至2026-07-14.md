# 地质找矿智能问答系统开发实习日志

> 实习时间：2026 年 6 月 25 日至 2026 年 7 月 14 日  
> 项目名称：地理知识图谱与 RAG 增强的智能问答系统（中期为国土空间规划方向，终期调整为地质找矿方向）
> 记录方式：按日期分别记录前端、数据端和后端工作；数据端、后端每条约 150 字，前端适当精简；各端每天另附约 50 字个人心得，可供三名成员分别整理个人实习日志。

## 6 月 25 日（星期四）｜实习动员与选题部署

**前端：** 上午 8:00 参加实习动员大会，了解分组、考核和选题要求。我负责前端方向，初步确定登录、智能问答、地图、知识图谱和后台五类页面，并梳理提问、查看来源及地图定位等核心操作，为需求分析做准备。

**个人心得（前端）：** 第一次从完整产品角度思考前端，我认识到页面美观只是基础，更重要的是围绕用户任务组织信息与操作流程。

**数据端：** 参加动员会后明确承担 Python 数据预处理与知识图谱构建工作。我与组员讨论 PDF 地理资料如何转化为可检索知识，初步把流程拆为文档解析、文本切片、向量化、实体关系抽取和 Neo4j 写入五部分，同时梳理可能使用的 pdfplumber、jieba、scikit-learn 等工具，形成个人学习清单和资料准备计划。

**个人心得（数据端）：** 数据端虽然不直接面对用户，却决定了答案的知识基础。我体会到先明确数据流和质量目标，比急于选择复杂模型更重要。

**后端：** 动员会后确定由我负责 Node.js 后端及三端集成。结合选题方向，我初步分析系统需要统一承接用户鉴权、问答请求、向量检索、知识图谱查询和大模型调用，并与组员约定前端、后端、数据端的职责边界。当天整理了 Express、SQLite、Neo4j 和 DeepSeek 的技术调研项，为总体架构设计和选题报告分工奠定基础。

**个人心得（后端）：** 我认识到后端不仅是编写接口，还承担连接三端的协调职责。尽早讲清模块边界，能减少后续重复开发和沟通成本。

## 6 月 26 日（星期五）｜需求调研与功能梳理

**前端：** 从普通用户和管理员两类角色梳理需求：用户需要提问、查看回答与来源、浏览图谱和地图；管理员还要管理文档、实体及问答记录。我据此整理页面跳转关系，明确问答页为主入口，地图和图谱负责解释结果。

**个人心得（前端）：** 按角色梳理需求让我意识到，同一套系统面对不同用户时重点完全不同，界面设计必须服务具体任务，不能简单堆放功能。

**数据端：** 围绕国土空间规划的中期选题收集政策 PDF 和术语资料，检查文本是否可复制、页码是否稳定以及表格是否影响解析。通过小样分析，我认识到规则明确的用地分类适合正则抽取，开放性的规划概念更适合由 LLM 提取；RAG 侧则需保留文档标题、页码和原文片段，才能在回答中实现可靠溯源。

**个人心得（数据端）：** 小样分析说明不存在适合所有资料的抽取方法。只有先观察文档结构，再选择规则、模型或人工校验，结果才更可靠。

**后端：** 今天重点完成需求到服务能力的映射。我把系统接口分为登录鉴权、智能问答、图谱子图、文档管理四组，并明确问答接口必须同时接收 RAG 文档片段和 KG 关系路径。针对答辩现场网络或数据库可能异常的问题，提前提出 LLM、Neo4j 和检索服务均需提供降级策略，保证部分依赖不可用时系统仍能返回可解释结果。

**个人心得（后端）：** 今天让我认识到异常路径也属于正式需求。若只设计成功流程，任何外部服务波动都会让系统失去可用性和演示稳定性。

## 6 月 27 日（星期六）｜总体设计与技术选型

**前端：** 完成低保真页面设计，确定侧边导航、顶部标题和内容工作区，细化问答页的会话列表、消息区、输入框及来源卡片。技术上选择 Vue 3、TypeScript、Pinia 和 Element Plus，并为图表、图谱与地图预留位置。

**个人心得（前端）：** 低保真原型能快速暴露信息层级问题，也让我明白应先验证结构和流程，再投入时间处理颜色、字体等视觉细节。

**数据端：** 今天设计离线预处理总体流程：逐页解析 PDF，按固定窗口和重叠区切片，使用 jieba 分词与 TF-IDF 建索引，将文档及 chunk 元数据写入 SQLite，再提取实体关系并写入 Neo4j。我特别确定了标题、页码、切片序号、字符范围等字段，确保后续检索结果能够定位回原文，也便于增量处理和质量检查。

**个人心得（数据端）：** 我体会到标题、页码和字符范围并非附属字段，它们决定了检索结果能否追溯。完整元数据和向量本身同样重要。

**后端：** 完成系统三层架构草案：Vue 前端通过 `/api` 访问 Express，后端并行调用检索与 Neo4j，再将上下文送入 LLM；Python 端离线生成 SQLite、模型文件和图谱数据。我同步设计共享类型，规划问答、图谱、管理、鉴权路由及检索、LLM 服务，使模块职责清晰并可独立测试。

**个人心得（后端）：** 架构设计的价值在于控制变化范围。把检索、图谱和大模型封装为独立服务后，后续替换算法时不会牵动整条链路。

## 6 月 28 日（星期日）｜环境搭建与协作准备

**前端：** 配置 Node.js 和前端开发环境，验证 Vite、Vue 3、TypeScript、Element Plus 自动导入及路径别名。建立页面、组件、状态仓库、API、类型和全局样式目录，并通过最小页面确认热更新与 hash 路由可用。

**个人心得（前端）：** 提前统一环境和目录看似耗时，实际能避免多人开发时出现导入混乱和版本差异，为后续快速编码提供稳定基础。

**数据端：** 配置 Python 环境及 PDF 解析、分词、向量化、Neo4j 和 Flask 依赖，检查本地 Neo4j Browser 与 Bolt 端口连接。使用短文本尝试中文分词和向量化，记录模型、SQLite 与解析缓存的输出位置；同时准备配置模板，将 API Key 和数据库密码留在本地，避免提交仓库。

**个人心得（数据端）：** 环境配置让我更加重视可复现性和安全性。依赖版本、输出路径与敏感配置若不规范，换一台机器就可能无法运行。

**后端：** 搭建 Node.js、TypeScript 和 Express 环境，调研 SQLite、Neo4j 驱动、OpenAI 兼容 SDK 与 dotenv。与前端统一开发端口和 Vite 代理规则，与数据端确认数据库位置、Neo4j 参数及检索格式。当天建立环境变量模板，明确密钥和密码不得进入版本库。

**个人心得（后端）：** 三端联调中的很多故障并非代码逻辑错误，而是端口、路径和配置不一致。建立共同约定能明显降低排查成本。

## 6 月 29 日（星期一）｜选题报告与详细设计

**前端：** 上午 8:00 参加选题报告，汇报系统需求、页面模块和开发计划，并说明地图与知识图谱的可视化价值。会后完成视觉与骨架设计文档，确定专业的期刊式风格，整理色彩、字体、间距 Token 和四个主页面结构。

**个人心得（前端）：** 汇报使我认识到可视化不是装饰，而是帮助用户理解空间位置和知识关系的工具，设计必须服务系统的专业表达。

**数据端：** 在选题报告中说明知识库构建方案，重点介绍 PDF 解析、切片、向量检索、实体抽取和 Neo4j 图谱的离线流程，以及 RAG 提供原文证据、KG 提供关系语义的互补作用。根据老师反馈，我进一步区分确定性规则抽取与 LLM 概念抽取的适用范围，并制定先用 TF-IDF 跑通、终期再升级 BERT/BGE 的分阶段目标。

**个人心得（数据端）：** 老师的反馈让我明白技术方案需要分阶段落地。先建立可运行基线，再用指标验证升级效果，比一次追求最复杂方案稳妥。

**后端：** 选题报告中负责讲解系统总体架构与在线问答流程：用户问题进入 Express 后，同时执行文档检索与图谱查询，合并上下文后调用大模型，最终返回答案、来源和关系链。会后依据评审意见补充异常降级、接口鉴权和模块解耦方案，明确先实现稳定的 JSON 接口，再扩展 SSE 流式输出和多模型互备。

**个人心得（后端）：** 对外讲解架构促使我重新检查每个模块的必要性。我体会到好架构不仅能够实现，还应让他人快速理解数据如何流动。

## 6 月 30 日（星期二）｜任务拆分与接口约定

**前端：** 将前端骨架拆成项目初始化、设计 Token、共享类型、路由、布局、请求封装、Pinia、聊天组件和业务页面等任务。先确定消息、来源、会话和文档类型，并约定 token 拦截与 401 处理，使页面可依靠 mock 数据并行开发。

**个人心得（前端）：** 将大页面拆成类型、组件和状态任务后，开发顺序更加清晰。我认识到共享数据结构是前端多人协作的重要基础。

**数据端：** 细化预处理脚本的输入输出和验收标准，确定切片默认采用 512 字符窗口与 128 字符重叠，并优先在段落或标点处截断。设计 SQLite 的 `documents`、`chunks` 表及向量字段，规划解析、切片、索引、概念抽取、图谱写入的单元测试。这样每一步既可独立验证，也能由总管线统一串联。

**个人心得（数据端）：** 把管线拆成可验证步骤后，问题能够定位到具体环节。我体会到清晰的输入输出和验收标准比单个脚本写得复杂更有价值。

**后端：** 今天将接口契约落实到具体字段，问答请求包含问题和流式开关，响应包含答案、来源与 KG 路径；图谱接口返回节点和边，管理接口返回文档统计。同步规划配置校验、中文分词、数据库访问和 LLM Prompt 组装方式，并与前端约定 `/api` 代理和错误结构，与数据端约定 `/search` 的 Top-K 检索格式。

**个人心得（后端）：** 接口字段一旦被多端使用，修改成本会迅速增加。今天让我更加重视契约先行、统一命名以及错误响应的一致性。

## 7 月 1 日（星期三）｜编码前准备与原型验证

**前端：** 按任务清单搭建 Vue 工程，验证自动导入、Scoped CSS、路由和 Pinia，并把视觉 Token 转成全局 CSS 变量。依据原型检查长文本、会话列表和后台表格布局，完成代码目录与组件边界确认。

**个人心得（前端）：** 实际原型比静态草图更容易发现长文本和窗口尺寸问题，尽早试运行能避免后期在多个页面重复修补布局。

**数据端：** 准备两类样本文档和测试用例，分别验证逐页文本提取、空白清洗、页码保留和中文断句效果。对切片结果重点检查过短片段、跨页内容及重叠重复，拟定平均长度和总数统计输出；同时整理 Neo4j 节点、关系命名规范，使 Python 抽取结果能够直接被后端 Cypher 查询和前端图谱展示使用。

**个人心得（数据端）：** 样本文档中的空页、断行和跨页内容提醒我，真实数据远比理想输入复杂，测试必须覆盖边界情况而非只看正常样例。

**后端：** 根据接口设计建立 Express 项目结构和 TypeScript 配置，验证 ESM 模块、dotenv 与本地启动脚本。先用静态语料模拟 RAG 与 KG 结果，推演问答路由中并行检索、Prompt 拼接、LLM 调用及错误返回的顺序，并检查前后端类型是否一致。通过这次原型验证，明确后端必须把检索服务封装成可替换模块。

**个人心得（后端）：** 在正式接入数据库前使用静态语料验证流程，可以先发现控制逻辑和类型问题。我认识到原型也是降低集成风险的手段。

## 7 月 2 日（星期四）｜前端骨架集中实现

**前端：** 完成 Vue 3 前端骨架，建立 hash 路由、侧边布局、类型、axios 和 Pinia，实现问答、地图、图谱、后台页面及聊天、来源、统计组件。随后补充登录、mock JWT、路由守卫、侧栏折叠、消息缓存与错误处理。

**个人心得（前端）：** 完成骨架后，我体会到稳定的路由、状态和请求层能够支撑页面快速扩展，基础结构比单个页面效果更值得优先投入。

**数据端：** 配合前端骨架确认数据展示字段，提供文档标题、页码、片段内容、相关度和实体关系的样例，检查 SourceCard 与图谱节点所需信息是否能由管线产出。与此同时继续完善预处理模块接口和测试样本，确保 SQLite 与 Neo4j 的字段命名不会在后续对接时频繁调整，并准备开始实际脚本编码。

**个人心得（数据端）：** 与前端对齐字段让我看到数据价值最终要通过界面表达。只完成抽取还不够，结果必须具有稳定结构并方便用户理解。

**后端：** 对照已完成的前端 API 层复核后端路由设计，统一登录、问答、图谱和文档列表的 URL、请求方法及响应字段。针对前端已实现的 token 拦截、消息缓存和 mock 降级，补充真实服务接入注意事项；同时细化 Express 中间件、SQLite 访问、Neo4j 会话和 LLM 服务的目录结构，为后续两天集中开发做准备。

**个人心得（后端）：** 前端页面使抽象接口变得具体，也暴露了部分字段遗漏。我体会到接口设计必须结合真实消费场景，而不能只从后端方便出发。

## 7 月 3 日（星期五）｜三端核心模块开发

**前端：** 对骨架进行构建检查，测试会话切换、发送状态、错误提示、侧栏折叠、管理员标签页和路由守卫。清理页面硬编码数据，将请求统一收口到 API 模块，并完善空列表、加载中及失败状态，为接入真实后端做准备。

**个人心得（前端）：** 加载、空数据和失败状态同样属于完整体验。今天让我认识到用户看到的不只是成功结果，还有系统等待与出错时的反馈。

**数据端：** 开始实现 PDF 解析、文本切片、索引构建、概念抽取和 Neo4j 写入脚本。先完成逐页解析与清洗，再实现带重叠的切片及 TF-IDF 建模，随后设计 LLM JSON 的容错解析和图谱批量写入。每个模块同步编写单脚本断言，便于定位页码、向量维度或关系错误。

**个人心得（数据端）：** 边开发边写断言能及时发现字段和维度错误。我体会到数据管线的正确性应靠可重复检查保证，而不是凭几条结果判断。

**后端：** 集中实现 Express 后端主体，包括配置加载、SQLite 数据层、中文分词、TF-IDF 检索、Neo4j 查询和 DeepSeek 调用。完成登录、问答、图谱子图和文档管理接口，并用种子语料联调。开发中重点处理 ESM 路径、原生依赖和数据库连接释放问题。

**个人心得（后端）：** 多种数据库和 SDK 同时接入后，资源释放与模块边界变得格外重要。后端稳定性往往取决于这些不显眼的细节。

## 7 月 4 日（星期六）｜预处理运行与接口联调

**前端：** 将 API 从 mock 切换为真实后端调用，通过 Vite 代理测试登录、问答、文档列表和图谱数据。补充加载、空结果与错误状态，检查来源卡片的标题、页码和摘要显示，并与后端统一字段命名，保留 mock 作为降级方案。

**个人心得（前端）：** 真实接口会暴露 mock 数据掩盖的延迟和字段差异。我认识到前端不能假设数据永远完整，应主动处理各种返回状态。

**数据端：** 首次串联 PDF 解析、512/128 切片、TF-IDF、SQLite 和 Neo4j 写入流程，在样本文档上检查 chunk 数量、词表规模、节点数及关系数。针对 PDF 断行、概念名称粘连和重复实体问题增加清洗规则，修正配置路径与模型输出，并将五个步骤封装到 `run_pipeline.py`，为中期联调提供真实数据产物。

**个人心得（数据端）：** 第一次跑通全流程比单独优化某个算法更有意义，因为它暴露了步骤间的数据兼容问题，也建立了后续改进的基线。

**后端：** 完成后端主要接口并与前端、数据端进行第一次联调，将 Python 产出的 SQLite 和 Neo4j 数据接入问答链路。修正检索模型配置、路径和响应映射问题，确认问题可以同时命中文档片段与关系路径，再由 LLM 生成回答。同步增加数据库或模型不可用时返回空结果的容错，避免单个依赖导致接口整体崩溃。

**个人心得（后端）：** 首次联调让我发现可观测信息非常重要。清楚记录请求路径、命中数量和异常来源，能让跨端问题更快定位。

## 7 月 5 日（星期日）｜中期前全链路集成

**前端：** 将图谱页接入 Neo4j 真实数据，问答页补充 Markdown、KG 标签、错误反馈、自动标题、localStorage 和加载骨架屏，后台加入真实统计与图表。随后配合 SSE、JWT 和双角色布局联调，准备中期演示页面与测试问题。

**个人心得（前端）：** 真实数据接入后，页面状态明显比 mock 阶段复杂。我体会到组件既要展示内容，也要稳定处理持续更新和异步状态。

**个人心得（后端）：** 复盘让我看到系统边界越多，失败组合就越复杂。明确每个服务的超时、重试和回退责任，才能避免异常扩散。

## 7 月 8 日（星期三）｜BERT/BGE 方案设计

**前端：** 配合语义检索升级检查数据契约，确认 TF-IDF 更换为 BGE 不影响来源和消息结构。梳理消息增加空间数据的方案，分析 SSE 三类事件及 AMap 初始化时机，准备在类型层统一定义点、线和图层数据。

**个人心得（前端）：** 算法升级没有引起页面改动，说明稳定契约发挥了作用。我认识到前端应依赖业务结构，而不是依赖后端实现细节。

**数据端：** 完成 BERT-NER 与 BGE 的详细设计，确定使用中文 BERT 做五类实体识别，以主力类别 F1 和覆盖率分层验收；检索采用 512 维 `bge-small-zh-v1.5`，并保留 BGE/TF-IDF 降级开关。同步制定环境验证、数据清洗、8:1:1 划分、训练、评估和 Flask 接入任务。

**个人心得（数据端）：** 详细设计让我把训练目标、数据划分和验收指标联系起来。模型开发必须可复现、可比较，不能只关注最终分数。

**后端：** 依据数据端方案调整集成设计，明确后端仍通过 Flask `/search` 获取统一 chunk 结果，不直接绑定具体向量模型；新增 `/ner` 只作为能力接口，不侵入核心问答路由。复核 TF-IDF 客户端的字段映射和异常返回，确保 BGE 启用后分数、标题、页码和片段格式不变，并规划在后台展示当前检索与 NER 状态。

**个人心得（后端）：** 通过服务接口隔离算法后，数据端可以独立升级模型。我体会到合理抽象不是增加层次，而是保护稳定的业务流程。
