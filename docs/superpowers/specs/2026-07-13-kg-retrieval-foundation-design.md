# KG 检索基础修复与 BGE 融合重排设计

> 日期：2026-07-13
> 状态：已完成方案确认，待用户审阅书面规格

## 1. 背景与问题

当前问答链路把 BGE 文本检索和 Neo4j 知识图谱检索并行执行，再分别放入 Prompt。这样能让回答同时看到文档片段和图谱关系，但两路结果互不影响：KG 命中并不会改变 BGE 文档的排序。因此，现有“混合检索”更准确地说是“上下文拼接”，还不是证据层面的融合检索。

进一步审计发现，现有 KG 检索还不适合直接参与 RAG 重排：

- 问题词“什么、哪些”等会作为关键词进入 Neo4j；
- 最多五个关键词分别执行一次 Cypher，查询串行且重复扫描；
- `CONTAINS` 查询没有相关度得分和稳定排序；
- OWL 全局补充结果先写入列表，可能占满十条名额；
- 问答 KG 查询只有一跳，不能把区域、矿床、构造、围岩和年代组成可解释线索；
- Neo4j 目前没有 `Region` 节点、`LIES_IN` 关系和坐标，无法理解“攀西”等区域限定；
- 全量管线调用 `write_to_neo4j()` 时漏传 `classifications`，可能导致 `owlTypes` 未写回。

所以本次改造分成两个严格顺序的阶段：先修复 KG 的正确性、可解释性、性能和区域数据基础，再允许 KG 影响 BGE 结果顺序。

## 2. 目标

### 2.1 Stage 0：修好 KG 基础

1. 从问题中提取有效地质关键词，过滤疑问词、语气词和重复词。
2. 将多个关键词合并为一次 Neo4j 查询，减少往返和重复扫描。
3. 为每条 KG 路径计算可解释分数，并按稳定规则排序。
4. 优先返回问题中明确提到的实体和区域，限制全局 OWL 补充结果数量。
5. 导入十个演示成矿区域及核心锚点关系，使区域问题能真正命中 KG。
6. 明确区分真实数据、OWL 推理关系和演示关系，避免把演示数据表述为真实勘查结论。
7. 修复 OWL 分类写回管线问题。

### 2.2 Stage 1：KG 感知的 BGE 重排

1. BGE 继续作为主检索器，保留其原始语义相关度。
2. KG 不替代 BGE，而是为 BGE 候选片段提供有上限的证据加分。
3. 只有通过最低语义门槛的文档片段才允许接受 KG 加分。
4. 最终 Prompt 使用重排后的文档片段和对应 KG 路径，而不是两个无关联列表。

## 3. 非目标

- 不把 TF-IDF 作为本次优化重点；它只保留为对照和应急模式。
- 不导入空间 mock 中生成的 1300 多个外围卫星点。
- 不把演示关系伪装成文献抽取结果或真实勘查结论。
- 不在线运行 HermiT，也不在每次用户提问时重建 OWL。
- 不在本次设计中引入新的向量数据库或独立 reranker 模型。
- 不改变知识图谱页面现有的二跳子图职责；问答检索和图谱可视化继续使用不同的结果规模。

## 4. 总体架构

```text
用户问题
   │
   ├─ 问题分析：分词、停用词过滤、区域/实体/关系意图识别
   │
   ├─ BGE：召回较宽的候选文档集
   │
   └─ KG：一次组合查询 → 路径评分 → 主结果 + 少量 OWL 补充
              │
              └─ Stage 1：把 KG 路径转成候选片段的证据加分
                         │
                         └─ 语义门槛过滤 + 融合重排
                                    │
                                    └─ Prompt：文档证据 + 对应图谱证据 + 来源属性
```

Stage 0 上线后，即使 Stage 1 尚未启用，KG 返回结果也应比当前实现更准确、更快且可解释。Stage 1 只消费 Stage 0 的稳定结果，不绕过其数据来源和安全约束。

## 5. Stage 0 详细设计

### 5.1 问题分析

新增独立的 KG 查询分析单元，输入为原始问题，输出为：

```ts
interface KGQueryAnalysis {
  keywords: string[]
  entityTerms: string[]
  regionTerms: string[]
  relationIntents: KGRelationType[]
  owlRules: string[]
}
```

处理顺序：

1. 使用现有 `nodejieba` 分词。
2. 清理空白和标点，统一同义表达，例如“构造控制、受控、控矿”归一为 `CONTROLLED_BY` 意图。
3. 过滤通用疑问词和问答噪声词，包括“什么、哪些、怎么、如何、是否、有没有、介绍、一下、相关”。
4. 去重并删除被更长词覆盖的短词。例如同时得到“钒钛”和“钒钛磁铁矿”时，优先保留后者。
5. 最多保留八个有效关键词；区域词、明确实体词和关系意图不受普通词截断顺序影响。

停用词和关系意图词表放在可单测的常量或纯函数模块中，不散落在 Cypher 拼接代码里。

### 5.2 一次组合查询

当前“每个关键词执行一次查询”改为一次带参数的组合查询。Cypher 接收 `keywords`、`regionTerms`、`relationIntents`、`owlRules` 和可选 `entityTypes`，在同一个 `session.run()` 中组成三个候选池：

1. **直接路径**：名称命中关键词的实体及其一跳关系；
2. **区域路径**：先匹配 `Region`，再沿 `LIES_IN` 反向找到区域内锚点，并展开锚点的一跳地质关系；
3. **OWL 补充**：只查询被问题意图触发的物化 OWL 分类及其支撑关系。

因此，“攀西钒钛磁铁矿受什么构造控制”不仅能返回“矿床位于攀西”，还可在同一次查询中得到“攀西区域内矿床受某断裂控制”。这属于有边界的区域二跳，不把整个问答查询扩展为无约束多跳。

查询返回原始关系类型、节点类型、坐标、OWL 类型、`inferred`、`isMock`、`source`，以及命中的关键词。中文关系名只在 TypeScript 映射层生成，评分使用稳定的英文关系类型。

三个候选池合并后按“直接/区域优先于 OWL、端点名称、关系类型”做数据库侧稳定排序，最多返回 60 条，再由应用层完成统一评分、去重和名额分配。候选集必须有确定性排序兜底：关系类型、起点名称、终点名称相同的输入应得到相同输出。

### 5.3 KG 路径评分

每条路径返回总分和评分原因：

```ts
interface KGPathScoreReason {
  code: 'exact_entity' | 'keyword' | 'region' | 'relation_intent' | 'owl_supplement'
  value: number
  detail: string
}
```

主路径评分规则：

| 条件 | 分值 | 上限 |
|---|---:|---:|
| 问题包含完整起点名称 | +40 | 40 |
| 问题包含完整终点名称 | +40 | 40 |
| 有效关键词命中端点名称 | 每个 +8 | 24 |
| 区域词命中 `Region` 端点，或路径锚点属于该区域 | +20 | 20 |
| 关系类型符合问题意图 | +20 | 20 |

同分时依次按“完整实体命中数、关系意图命中、非推理关系优先、起点名称、关系类型、终点名称”排序。`inferred=true` 不直接判为错误，但同分时排在原始关系之后。

OWL 全局查询只作为补充池，不参与挤占主路径：

- 仅在问题触发相应 OWL 意图时查询；
- 主路径先占结果名额；
- 全局 OWL 补充最多两条；
- 与主路径重复的关系去重；
- `scoreReasons` 明确标记 `owl_supplement`。

最终问答默认返回十条路径，其中至少八个名额留给问题实体和区域直接相关的主路径。

### 5.4 区域演示数据

导入以下十个 `Region` 节点，与现有空间演示数据保持同名：

1. 东天山成矿带
2. 攀西钒钛成矿带
3. 长江中下游成矿带
4. 胶东金成矿区
5. 滇黔桂成矿区
6. 秦岭成矿带
7. 南岭成矿带
8. 冈底斯-三江成矿带
9. 辽吉铁金成矿区
10. 白云鄂博稀土成矿区

每个区域只导入用于问答演示的核心锚点：现有 `spatial-mock.ts` 中十个区域定义的全部 43 个锚点矿床，以及这些锚点直接引用的构造、围岩、地质年代和矿床类型。允许复用 Neo4j 中已有的同名真实实体；不存在时才新建演示节点。导入数据整理为独立、可审阅的固定清单，运行时不解析 TypeScript 源文件。

典型关系链如下：

```text
攀枝花钒钛磁铁矿
  ├─ LIES_IN → 攀西钒钛成矿带
  ├─ CONTROLLED_BY → 攀枝花南北向断裂
  ├─ HOSTED_IN → 层状辉长岩
  └─ FORMED_IN → 晚二叠世
```

数据安全规则：

- 所有新建演示节点写入 `isMock: true`、`source: 'spatial-demo-v1'`。
- 复用的真实节点不改变 `isMock`，只给新建关系标记演示来源。
- 所有演示关系用 `MERGE (a)-[r:TYPE {source: 'spatial-demo-v1'}]->(b)` 独立创建，再写入 `isMock: true` 和中文 `display`。即使两端已有同类型真实关系，也不修改或复用真实关系。
- 演示坐标使用 `mockLng`、`mockLat`，绝不覆盖已有 `lng`、`lat`。
- 导入脚本使用 `MERGE`，重复执行不增加重复节点或关系。
- 删除脚本只删除 `source='spatial-demo-v1'` 的关系，以及已经孤立且同来源的演示节点。
- 不导入自动生成的外围卫星点。

### 5.5 OWL 分类写回修复

全量管线应同时传入推理关系和分类结果：

```python
write_to_neo4j(
    reason_stats["relations"],
    reason_stats["classifications"],
)
```

该修复必须先用失败测试证明：当 `run_reasoning()` 返回分类结果时，管线会把它传给 `write_to_neo4j()`。随后再修改生产代码。已有 Neo4j 数据不要求为了代码修复立即全量重跑；在验证脚本确认现有 `owlTypes` 不完整时，可单独执行 OWL 构建、推理和写回步骤。

### 5.6 数据契约

后端和前端的 `KGPath` 同步扩展：

```ts
interface KGPath {
  from: string
  relation: string
  relationType?: string
  to: string
  score?: number
  scoreReasons?: KGPathScoreReason[]
  inferred?: boolean
  isMock?: boolean
  source?: string
  regionContext?: string
  // 保留现有 owlTypes 和坐标字段
}
```

新增字段均为可选，以兼容已有对话缓存和旧接口响应。`relationType` 用于程序判断，`relation` 继续用于中文展示。

## 6. Stage 1 详细设计

### 6.1 扩大 BGE 候选集

最终需要 `topK` 条文档时，先由 BGE 召回 `max(topK * 3, 15)` 条候选。KG 查询仍与 BGE 召回并行执行，不增加前后依赖；融合发生在两路都返回之后。

### 6.2 语义门槛

KG 只能调整语义相关候选之间的次序，不能把明显无关文档抬到前列。候选片段须满足：

```text
bgeScore >= max(0.04, bestBgeScore * 0.45)
```

不满足门槛的片段不接受 KG 加分，也不进入最终结果。若全部候选未过门槛，沿用现有低相关性处理，不因 KG 演示关系强行生成文档结论。

### 6.3 KG 支持度

将 Stage 0 的高分路径转换为“问题实体、关联实体、关系意图”证据。对每个 BGE 候选片段计算：

```text
kgSupport = min(1,
  0.6 × 问题侧实体覆盖率
  + 0.3 × 路径关联实体覆盖率
  + 0.1 × 关系意图词覆盖率
)
```

覆盖判断使用规范化后的完整实体名，避免单字和泛化词误加分。演示路径可以参与排序，但必须把 `isMock/source` 继续传到回答阶段。

最终分数：

```text
finalScore = 0.8 × normalizedBgeScore + 0.2 × kgSupport
```

其中 `normalizedBgeScore = bgeScore / bestBgeScore`；`bestBgeScore` 不大于 0 时直接视为无有效候选。固定 20% 上限保证 BGE 始终是主检索器。若 KG 不可用或无有效路径，跳过融合公式并保持 BGE 原始分数和原始顺序；同分时按原 BGE 排名和 chunk id 稳定排序。

### 6.4 Prompt 组织

Prompt 不再只给出两个互不相关的列表，而按以下顺序组织：

1. 重排后的文档片段，保留文档名、页码、BGE 分数和融合分数。
2. 与这些片段或问题实体相关的 KG 路径。
3. 路径来源说明：文献关系、OWL 推理关系或演示关系。

系统提示词增加硬约束：

- 演示关系只能用于展示系统如何关联区域、矿床、构造、围岩和年代；
- 不得把演示关系写成已由文献证实的事实；
- 使用演示关系时，回答中必须出现“演示知识关系，不作为实际勘查结论”。

## 7. 前端体验

问答页继续显示 KG 关系标签，但增加来源状态：

- 原始关系：保持现有样式；
- OWL 推理：显示“本体推理”；
- 演示关系：显示“演示关系”，并在关系区显示“演示知识关系，不作为实际勘查结论”。

评分细节默认不占用普通用户界面。开发或答辩调试状态可在折叠详情中展示总分和 `scoreReasons`，用于说明“为什么系统返回这条关系”。旧消息没有新字段时仍能正常渲染。

## 8. 错误处理与降级

- Neo4j 不可用：KG 返回 `succeeded=false`，问答继续使用 BGE，不给出 KG 加分。
- KG 查询超时或语句失败：记录错误，不把空结果伪装成“图谱无知识”。
- 区域演示数据未导入：系统仍可查询原有实体，但区域限定不承诺命中。
- BGE 不可用：沿用现有检索配置的明确错误或备用策略，不让 KG 单独伪装成文档检索。
- 演示导入部分失败：事务回滚，不能留下半个区域的数据。
- Prompt 构建时只要存在任一 `isMock=true` 路径，就必须加入演示免责声明。

## 9. 测试策略

### 9.1 Stage 0 单元测试

- “攀西钒钛磁铁矿受什么构造控制”过滤“什么”，识别区域、实体和 `CONTROLLED_BY`。
- 长实体词覆盖短词，关键词顺序稳定且不重复。
- 路径评分中，攀西和钒钛磁铁矿直接相关路径排在全局矿床路径之前。
- OWL 补充最多两条，不能挤占八个主路径名额。
- 相同输入多次评分得到相同顺序。
- `KGPath` 的演示来源和评分原因正确映射。
- 管线把 `relations` 和 `classifications` 同时传给 Neo4j 写回函数。

### 9.2 演示数据脚本测试

- 首次导入创建预期的十个区域和核心关系。
- 第二次导入节点数、关系数不增加。
- 已有真实节点的 `lng/lat/isMock` 不被覆盖。
- 清理只移除 `spatial-demo-v1` 数据，不删除真实节点和真实关系。

### 9.3 Stage 1 单元测试

- KG 命中时，包含关联实体的 BGE 片段可在语义相近候选中上升。
- KG 无结果或不可用时，排序与原 BGE 顺序一致。
- 低于语义门槛的片段即使命中演示实体也不能进入最终结果。
- KG 加分上限为 20%，不会压过明显更高的 BGE 语义分。
- 融合分数相同时按原始排名和 chunk id 稳定排序。

### 9.4 集成与人工验收

使用至少以下问题验证：

1. “攀西钒钛磁铁矿受什么构造控制？”
2. “攀枝花钒钛磁铁矿赋存在哪类岩石中？”
3. “哪些矿产受构造控制？”
4. “胶东金矿和断裂有什么关系？”
5. “介绍一下完全无关的医学问题。”

验收指标：

- 示例 1 的前列 KG 路径包含攀西或攀枝花相关实体，不再被方铅矿等全局结果占满。
- KG 组合查询只发生一次主查询，数据库往返数不随关键词数线性增加。
- 当前规模下，KG 主查询目标耗时不高于现状，并以本机重复测试的中位数记录结果。
- 示例 1、2、4 使用演示关系时，前端和回答都出现演示免责声明。
- Stage 1 开启后能展示至少一个“KG 改变 BGE 候选顺序”的可复现实例。
- Neo4j 关闭时，BGE 问答仍可完成，且不显示虚假的 KG 关系。

## 10. 实施范围与顺序

预计涉及：

- `backend/src/services/kg.ts` 及拆出的纯分析/评分模块；
- `backend/src/services/tokenizer.ts`；
- `backend/src/routes/qa.ts`；
- `backend/src/services/llm.ts`；
- `backend/src/types/index.ts` 与 `frontend/src/types/index.ts`；
- `frontend/src/components/ChatMessage.vue`；
- `ml-service/scripts/run_pipeline.py`；
- 新增可重复执行的区域演示数据导入/清理脚本；
- 对应的 TypeScript、Python 和接口测试。

实施严格按以下顺序推进：

1. 先写失败测试，修复 OWL 分类写回。
2. 先写失败测试，实现问题分析和路径评分纯函数。
3. 把 KG 主检索改为一次组合查询，并验证排序和性能。
4. 导入十个区域及核心锚点关系，验证幂等和清理。
5. 扩展接口、Prompt 和前端演示来源提示。
6. 在 Stage 0 验收通过后，再写失败测试实现 BGE 候选扩召与 KG 融合重排。
7. 完成端到端问答、降级和人工答辩示例验证。

Stage 0 未通过准确性、来源标记和幂等验收时，不启用 Stage 1。
